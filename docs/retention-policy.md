# Keystone — data retention policy

**Requirements:** SPEC **R21** (privacy-safe logging with a documented retention policy) and
**R26** (PII redaction in stored logs + a documented retention policy).
**Implementation:** `service/recon/privacy.py` (`RETENTION`, `run_purge`) and
`service/recon/logging.py` (`LOG_MODE`).
**Tests:** `service/tests/privacy/` — including
`test_retention_policy_doc.py`, which parses the schedule table below and fails if it stops
matching `recon.privacy.RETENTION`. This document cannot drift from the code without turning
the suite red.

---

## 1. What this policy governs

Every source record in Keystone is synthetic, generated by `recon.seed`. The policy is written
as though it were not, because the point of the deliverable is the mechanism.

Keystone holds personal data in three places, and they are treated differently:

| layer | tables | why it holds personal data |
|---|---|---|
| **landing + staging** | `raw_records`, `stg_*` | verbatim and normalised copies of the source records |
| **evidence + decisions** | `field_lineage`, `invariant_results`, `conflicts`, `proposals`, `proposal_events`, `entity_link_candidates`, `ingest_runs`, `source_generations` | the values a rule compared, quoted back so a reviewer can judge the call |
| **canonical + audit** | `entities`, `audit_log` | the product of the service, and the record of what it did |

The fields that carry it are the ones `docs/invariant-contract.md` §1 defines: `email`,
`guardian_email`, `guardian2_email`, `payer_email`, `billing_owner_email`, `first_name`,
`last_name`, `payer_name`, the payments `metadata.student_first_name` / `student_last_name`
pair, `crm.deal.name` (which carries the household surname), `dob`, `student_number`,
`household_id`, and the two consent flags `marketing_consent` and `communication_opt_out`.
**The dataset contains no phone number**, and no phone pattern has been invented for one — an
unrecognised key is redacted anyway, because the redactor is default-deny (§4).

## 2. The retention schedule

One row per rule, in the order `run_purge` executes them. `--` means the table has no
time-based window.

| table | timestamp column | window (days) | disposition | columns rewritten |
|---|---|---|---|---|
| `stg_crm_contact` | materialized_at | 30 | purge | -- |
| `stg_crm_deal` | materialized_at | 30 | purge | -- |
| `stg_student` | materialized_at | 30 | purge | -- |
| `stg_enrollment` | materialized_at | 30 | purge | -- |
| `stg_payment` | materialized_at | 30 | purge | -- |
| `entity_link_candidates` | created_at | 90 | purge | -- |
| `raw_records` | ingest_ts | 90 | purge | -- |
| `ingest_runs` | started_at | 90 | anonymize | error_detail |
| `source_generations` | updated_at | 90 | anonymize | error_detail |
| `field_lineage` | observed_ts | 180 | purge | -- |
| `invariant_results` | created_at | 180 | anonymize | detail |
| `proposal_events` | ts | 365 | purge | -- |
| `proposals` | created_at | 365 | purge | -- |
| `conflicts` | created_at | 365 | anonymize | entity_refs, observed_values |
| `conflict_incidents` | created_at | 730 | purge | -- |
| `conflicts` | created_at | 730 | purge | -- |
| `audit_log` | ts | 730 | purge | -- |
| `entities` | -- | -- | retain | -- |
| `entity_links` | -- | -- | retain | -- |
| `api_clients` | -- | -- | retain | -- |
| `budget_ledger` | -- | -- | retain | -- |
| `budget_reservations` | -- | -- | retain | -- |
| `incidents` | -- | -- | retain | -- |

### 2.1 Why each window is what it is

**`stg_*` — 30 days, purged.** Staging is a derived cache of normalised source values. It is
the only copy of personal data in the system that can be rebuilt on demand from the landing
table, so it gets the shortest window. It is also the only place any application role is
permitted to DELETE (`recon_writer`, migration 0002), precisely because it is re-materialisable.

**`entity_link_candidates` — 90 days, purged.** Accepted and rejected ER candidates with their
scoring detail. They explain a link decision for as long as the generation that produced it is
still explainable, which is the landing window.

**`raw_records` — 90 days, purged.** Verbatim source payloads: the largest raw-PII store in the
system. Held long enough to re-materialise staging and to re-run the three ingested generations
the person-key stability check needs (contract §9.2) — one quarter. Two consequences are
accepted deliberately and are stated here rather than discovered later:

* the `entity_links` provenance floor (trigger `entity_links_require_raw_record`, SQLSTATE
  `KS009`) is **verifiable only inside this window**. Older links still name a landing record;
  that record is gone;
* because that trigger fires on UPDATE as well as INSERT, an `entity_links` row whose landing
  record has been purged can no longer be UPDATEd **at all**. It can only be read or deleted.

**`ingest_runs` — 90 days, `error_detail` anonymized; row retained forever.** The row itself is
load-bearing rather than logging: absence-style invariants (C5/C8) must be skipped for a source
whose run is not `ok`, and that decision is made from this table. Deleting the row would change
detection behaviour. Only `error_detail`, which quotes rejected records, is redacted — on the
same clock as the landing table it describes.

**`source_generations` — 90 days, `error_detail` anonymized; row retained forever.** Same
reasoning: the per-source completeness ledger (migration 0009) decides whether an absence rule
may run, so the counts and the `complete` flag are permanent and only the error packet ages out.

**`field_lineage` — 180 days, purged.** `value_text` holds per-field personal values across
generations. Oscillation detection is a window scan for A,B,A over this table; two quarters
covers the three ingested generations with margin, and nothing reads lineage older than that.

**`invariant_results` — 180 days, `detail` anonymized; row retained forever.** Per-record
verdicts *are* the grading contract and are never overwritten per run, so the verdict, the rule
id and the record ref survive indefinitely. The `detail` packet, which quotes the values that
failed the rule, does not.

**`proposal_events` — 365 days, purged.** `before` and `after` are full canonical snapshots.
They exist to make a rollback possible; a year after the apply, the reversal is no longer a live
operation. Purged ahead of the proposal that owns them.

**`proposals` — 365 days, purged whole.** `evidence`, `action` and `rationale` all quote
personal values. **They cannot be anonymized in place by anybody** — migration 0005's
`proposals_payload_is_immutable` trigger raises SQLSTATE `KS005` for the schema owner as well as
for every application role, which `tests/privacy/test_purge.py::test_proposal_evidence_cannot_be_anonymised`
asserts against the live database. The only disposition the write boundary leaves available is
deleting the row. What survives as the record of the decision is the `audit_log` entry written
at decision time, which under the default `LOG_MODE=safe` was already redacted when it was
written.

**`conflicts` — two stages: anonymized at 365 days, purged at 730.** `observed_values` holds the
disagreeing personal values themselves and `entity_refs` can carry an address. A conflict is
referenced by its proposals, so it cannot be deleted while they survive; it is anonymized in
place at one year instead, keeping the `fingerprint`, `type` and `status` that make re-detection
idempotent. The row itself goes at two years, once no proposal and no incident membership
references it.

**`conflict_incidents` — 730 days, purged.** Two ids and a distance; no personal data of its
own. It is swept on the same clock as the conflict it points at and **before** it, because
otherwise it would block that conflict's DELETE forever.

**`audit_log` — 730 days, purged.** The accountability record, and under the default
`LOG_MODE=safe` already redacted at write time — so it is the lowest-risk copy in the system and
gets the longest window. It deliberately outlives the proposals it describes.

### 2.2 Tables with no window, and why

**`entities` — retained.** The canonical record is the service's *product*, not a log; ageing it
out would delete the output. `entities.current` is also UPDATE-blocked outside the cited-apply
path (SQLSTATE `KS001`). **Erasure of a named subject is a rights-request operation, not a
time-based sweep, and it is not built.** See §6.

**`entity_links` — retained.** `source_key` is the source's *natural key* — the trigger above
joins it to `raw_records.natural_key`. It is surrogate in the generated dataset (contract SS3),
but its content is chosen by the source, not by Keystone, so it is **not** treated as
non-personal: `source_key` is off the log allow-list and is tokenised like `natural_key` (§4.0).
The rows themselves are kept as long as the canonical rows they justify.

**`api_clients`, `budget_ledger`, `budget_reservations`, `incidents` — retained.** Key hashes,
money and cluster geometry. No personal data.

## 3. Purge vs anonymize, and the mechanism

**Purge** is `DELETE`. **Anonymize** is an in-place `UPDATE` that rewrites the named jsonb
columns through the same redactor the logger uses, so the row survives with its structure, its
field names and each value's kind, digest and shape, and without the value.

Which one a table gets is decided by **what the write boundary permits, not by preference**:

* a table with no UPDATE trigger and no dependents can be purged outright;
* a table whose row is load-bearing for detection (`ingest_runs`, `source_generations`,
  `invariant_results`) is anonymized, because deleting it would change behaviour;
* a table whose payload is frozen by a trigger (`proposals`, `KS005`) **cannot** be anonymized
  and is therefore purged whole.

### 3.1 Parents wait for their children

`DELETE FROM conflicts` while a proposal references it raises `23503`. Every purge rule with
dependents therefore carries a `NOT EXISTS` guard, and a parent whose child is still inside its
own window is **retained until the child ages out**. The three dependency graphs are
`stg_* → raw_records`, `proposal_events → proposals → conflicts`, and
`conflict_incidents → conflicts`. `RETENTION` is ordered so every dependent is swept first.

### 3.2 Running it

```python
from recon.privacy import run_purge
from recon.db import get_engine

with get_engine().begin() as conn:          # connects as the DATABASE_URL principal
    for result in run_purge(conn):          # add dry_run=True to count without writing
        print(result.table, result.disposition, result.rows)
```

`run_purge` opens no transaction of its own — the caller owns the transaction, so a sweep can be
inspected and rolled back. It writes one `audit_log` row per sweep
(`actor='system:retention'`, `action='retention.purge'`) containing **counts only**, never a
purged value. That row is built by `recon.logging.audit_row` like every other audit row in the
service, so its `detail` has the same `{mode, body_sha256, body}` shape §4 documents — the
sweep's summary is the `body`:

```json
{"mode": "safe",
 "body_sha256": "<sha256 of the canonical JSON of the summary>",
 "body": {"ran_at": "2026-08-22T12:00:00+00:00",
          "tables": [{"table": "raw_records", "disposition": "purge",
                      "window_days": 90, "rows": 12}]}}
```

It is idempotent: redaction is idempotent, so a second sweep over the same rows
rewrites nothing and deletes nothing.

`dry_run=True` counts against the database as it is *now*. For a table with dependents that
makes it a **lower bound** — a parent still blocked by a child this same sweep would delete is
reported as not-in-scope. Leaf tables are exact. This is deliberate: a second predicate that
could drift from the one the real `DELETE` uses would be worse than an under-report.

### 3.3 Which principal purges — and the grant that was *not* widened

**The sweep runs as the ops/migration principal named by `DATABASE_URL` — the schema owner, the
same principal that runs `alembic upgrade`. It is not something the application can do, and no
grant was widened to change that.**

Migrations 0001–0009 hand `DELETE` to exactly one non-owner grantee: `recon_writer` on the five
`stg_*` tables. No application role holds `DELETE` on `raw_records`, `field_lineage`,
`audit_log`, `invariant_results`, `conflicts`, `proposals`, `proposal_events`,
`entity_link_candidates`, `conflict_incidents` or `source_generations` — which is *correct*: the
detection path must not be able to erase its own evidence, and that is the same boundary R15 and
the three-role separation of duties rest on. Granting `recon_writer` the DELETE it would need to
purge would dismantle it.

So the sweep is an ops job, not a service job:

* `recon.privacy.assert_purge_principal` refuses to run as `recon_writer`, `review_writer` or
  `apply_writer`, raising `PurgeNotPermitted` rather than issuing DELETEs that a grant will
  reject halfway through the schedule;
* `tests/privacy/test_purge.py::test_no_writer_role_holds_delete_on_a_retention_table` asserts
  the grant set against `information_schema.role_table_grants`, so a future migration that
  widened one turns the suite red;
* scheduling follows the same route as every other Keystone job (DESIGN: Render cron → HTTPS +
  shared-secret header), but with the **ops** credentials, not the service role's. **The cron
  entry itself is not wired up in this ticket** — `run_purge` is a callable job with a
  transaction-owning caller, and nothing schedules it yet.

## 4. What redaction actually does (and does not)

`LOG_MODE=safe` is the default — in `recon.config.Settings`, in `recon.logging`, and in
`.env.example`. `LOG_MODE=full` stores raw bodies, is reachable only through the process
environment, is **development only**, and logs a warning every time it is configured.

### 4.0 Where redaction is applied

**At the sink, not at the call site — and there are four sinks.** This section used to say
"exactly two", and the two it did not name were the two nobody was watching. The list is now
`recon.logging.SINKS`, in code rather than in prose, and `tests/privacy/test_sinks.py` walks the
source against it, so a fifth sink fails the suite on the commit that adds it.

| sink | chokepoint | covers |
|---|---|---|
| structlog event | the `redaction_processor` in the configured chain (`recon.logging.configure_logging`) | every `log.info/warning/error` in the package, including values bound onto a logger and context variables |
| audit_log row | `recon.logging.audit_row` / `recon.logging.insert_audit_row` | `actor`, `action`, `subject`, `detail` and the three counters — **for the writers marked routed in `recon.logging.AUDIT_WRITERS`; see the gap below** |
| direct terminal write | `recon.logging.console` | the `python -m recon.suite` scorecard, and any other human-readable line written straight to stdout/stderr |
| stdlib logging record | `recon.logging._install_stdlib_bridge` (a `ProcessorFormatter` ending in the *same* `redaction_processor`) and `recon.logging.uvicorn_log_config` | uvicorn's access and error logs, sqlalchemy, alembic, httpx, anthropic, and captured `warnings` |

The last two were real leaks, not hypotheticals:

* **`print` / `traceback.print_exc`.** Three entry points wrote to the terminal with nothing in
  front of them, and `recon/suite/__main__.py` dumped a raw Python traceback — frame reprs
  included — for every exception escaping a check. The suite runner now emits that traceback as
  a structlog event with `exc_info`, so it is formatted *inside* the chain, and writes its
  scorecard through `console`. Four `print` sites remain in modules other tickets own; they are
  declared, with the exact one-line change each needs, in
  `recon.logging.UNROUTED_TERMINAL_WRITERS`, and the test fails if an undeclared one appears.
* **stdlib `logging`.** structlog's chain covers structlog loggers and nothing else, so
  `uvicorn.access` printed every request path and query string — caller-controlled text — verbatim
  to the same terminal as the redacted events beside it. `configure_logging` now installs a root
  handler whose formatter ends in the same redaction processor, and strips the handlers off the
  loggers in `recon.logging.CAPTURED_STDLIB_LOGGERS` so their records propagate to it. Each of
  those loggers also gets an explicit level, so installing the bridge changes **routing, not
  verbosity** — a privacy fix must not switch on every chatty client library as a side effect.

**The `audit_log` gap, stated rather than hidden.** `audit_row` is the chokepoint, but it has one
caller. `recon/budget.py` (`_audit`) and `recon/api/internal.py` (`claim_run`) both write
`INSERT INTO audit_log` directly and bind `actor`, `action` and `subject` **unredacted**,
redacting only `detail` through `audit_detail`. Those two modules belong to other tickets;
`recon.logging.AUDIT_WRITERS` records each one, marks it unrouted and carries the exact change
that routes it, and `tests/privacy/test_sinks.py` fails if a writer is added, or if one changes
status without the enumeration changing with it. Until they are routed, the honest statement is:
*every field of an audit row written through `recon.logging` is redacted; two writers elsewhere
in the package still bind three of their fields raw.*

**The HTTP response body is a sink too, and it is not on the list above because it is not a log.**
FastAPI's default `RequestValidationError` handler serialises pydantic's `input` member — for a
missing top-level field, the entire rejected object — into the 422 body, so a payload error
answered the caller with the record it had just refused. `recon.app` installs a handler that
returns an RFC7807 problem carrying `loc`, `type` and a scrubbed `msg`, and no `input` or `ctx`.
R2/R3 grade that a bad payload gets a structured 4xx, not that the 4xx is verbose.

A processor chain is process-wide state, so it only covers anything if the process installs it.
`recon.logging.configure_logging_once()` is called by every entry point listed in
`recon.logging.ENTRY_POINTS` — `recon/app.py`'s `create_app()` (what `make serve` and
`uvicorn … --factory` run), the `recon` CLI (`recon/__main__.py`), `python -m recon.seed`
(`recon/seed/__main__.py`), `python -m recon.suite` (`recon/suite/__main__.py`),
`python -m recon.bench` (`recon/bench/__main__.py`), and alembic's `migrations/env.py`. `tests/privacy/test_logging_installed.py` asserts each one still
does, imports the **real** application and asserts the *active* structlog configuration contains
the redaction processor, and runs each entry point in a subprocess to check the configuration a
real process ends up with.

`actor`, `action` and `subject` are allow-listed keys, so they are **scrubbed, not tokenised** —
an embedded address or student number is removed, the reference itself survives. That is
required, not a convenience: migration 0004's trigger (SQLSTATE `KS003`) matches `actor` against
`^system:`, and a tokenised `subject` would make `audit_log` unqueryable, which is the opposite
of the R15 accountability record it exists to be.

In safe mode, `audit_log.detail` is DESIGN's *hash + preview*:

```json
{"mode": "safe",
 "body_sha256": "<sha256 of the canonical JSON of the raw body>",
 "body":        {"guardian_email": "[pii:email:d5ff835ff355:aaaaaaa-aaaaaaaa-aaaa@aa~]", "grade": "6"}}
```

A token is `[pii:<kind>:<digest>:<shape>]`.

* **`digest`** is a truncated salted SHA-256 over the value's *normalised* form
  (`recon.normalize`), so one mailbox has one pseudonym across sources and generations and the
  log stays correlatable. The salt is a committed constant, because determinism is graded here
  and a per-deployment random salt would make the audit log uncorrelatable across restarts.
* **`shape`** is a character-class mask of the *raw* value — letters become `a`, digits become
  `9`, a small punctuation set survives. **It contains no character of the value.** A preview
  built from the first few characters of an address is a leak; this is not one. Because the
  shape comes from the raw value while the digest comes from the normalised one, the C4
  email-variance conflicts this project is graded on are still visible in a redacted log.
* Redaction is **default-deny**, in all three leaf positions:
  * a **value** is emitted verbatim only if its key is on a committed allow-list of operational,
    non-identifying keys (`recon.privacy.SAFE_KEYS`, `SAFE_KEY_PATTERNS`);
  * a **mapping key** is a leaf too — an evidence packet is keyed by field path *and* by observed
    value — so a key survives only if it is on a committed vocabulary of field *names*
    (`PII_KEYS` ∪ `TEXT_KEYS` ∪ `SAFE_KEYS` ∪ `STRUCTURAL_KEYS`). A key the vocabulary has not
    met comes out as a token: unreadable, never leaked, and one line in `SAFE_KEYS` to fix;
  * a **sequence element** has no key of its own, so it inherits none — except under a `PII_KEYS`
    key (every element of `{"first_name": […]}` *is* a first name) or a `SEQUENCE_SAFE_KEYS` key,
    whose elements come from a committed non-personal vocabulary (field names, refs, table names).
* **Value-shape detection covers four of the six kinds, and the docstring used to claim all six.**
  `recon.privacy.SHAPE_DETECTORS` is the whole of it: an email address, an `S-000000` student
  number, a bare ISO calendar date (`dob`) and an `HH-000000` household id. Those four are caught
  wherever they appear — under an allow-listed key, in an event name, in the middle of a sentence.
  `recon.privacy.SHAPELESS_KINDS` names the ones with no detector and says why. The one that
  matters is **`name`: a personal name is a word, and no pattern separates `Fairbank` from
  `Applied` or from `Lower School`.** It is not closed by shape, and the claim that it was is
  gone. It is closed by four other things — the `PII_KEYS` vocabulary, the keyed forms below, the
  sibling pass below, and by keeping source-controlled keys off the allow-list — and the residue
  is stated in §4.1.
* **Source-controlled keys are not allow-listed.** `natural_key` and `source_key` hold whatever
  the *source* calls its primary key, so their content is chosen upstream and cannot be safe by
  construction. They used to be on the allow-list, and a duplicate-primary-key rejection put a
  surname, a household id and a date of birth on the terminal of the running service in default
  safe mode. They are tokenised now (kind `opaque`, because the redactor cannot tell a surrogate
  id from a composite and does not guess); the token is deterministic, so two rows that share a
  natural key still visibly share one.
* **The sibling pass.** Before anything is walked, the values under a `PII_KEYS` key anywhere in
  the event are collected, and those literals are removed from the event's free-text and
  allow-listed strings too. That is what catches the second half of the leak above: the same
  rejection carried the key as a field *and* interpolated it bare into `detail`, where it had no
  shape and no adjacent key. It is a real control, not a substitute for the limit in §4.1 — a
  name appearing **only** in prose, under no key, in no other field of the same event, is still
  not findable.
* Redaction sees the **final string form** of every value. A value with no JSON spelling — an
  exception, a `UUID`, a `Decimal`, a `datetime` — is stringified *inside* the redactor, before
  any decision is taken about it, so nothing reaches the renderer that the redactor did not
  produce. Ordering, not decoration: an exception carrying a rejected record is how personal
  data most plausibly reaches a log in this system, because that is what the ingest path raises.
* Redaction is **recursive**. It reaches the leaves of jsonb evidence packets, action payloads
  and error details, because that is where the personal data in this schema actually is.

### 4.1 Honest limits

* **A token is a pseudonym, not anonymisation.** The salt is committed, so an attacker who can
  guess a value can confirm it. Low-cardinality fields are weaker still: `dob` and
  `student_number` are enumerable, and their tokens correlate records rather than protecting the
  value. Consent booleans get no digest at all (`[pii:flag:redacted]`), because hashing a
  two-valued domain *is* the value. **A row that has been "anonymized" by this policy is
  therefore pseudonymised, and should be treated as personal data of reduced sensitivity — not
  as anonymous data outside the scope of a rights request.**
* **A bare personal name in free prose cannot be shape-detected, and is not removed.** This is
  the limit, stated plainly because it is the one an overclaim would hide. A name has no shape.
  `"Zedail could not be matched"` names nobody's field, sits under no key, and appears nowhere
  else in the event — nothing in this module finds it. What *is* removed is a name that reaches
  the log in one of the four ways it actually reaches a log here: under a `PII_KEYS` key
  (tokenised); beside its key in any of four spellings — JSON `"first_name": "…"`, Python `repr`
  `'first_name': 'Amriyo'` (what every f-string, `%s`, `repr()` and traceback of a dict produces,
  and therefore the common case), Postgres' `Key (first_name)=(…)`, and a bare `first_name=…`;
  as a mapping **key**, which is default-deny like any other leaf; and as a literal that the same
  event also carries under a PII key (the sibling pass, §4.0). The bare `key=value` form stops at
  whitespace, so a multi-word value in that spelling is only partly removed. Callers must put
  source values in the structured `detail` mapping rather than interpolating them into a sentence;
  `recon.logging.audit_detail` is the supported path.
* **A `dob` is recognised only as a bare `YYYY-MM-DD`.** That is the one spelling
  `recon.normalize.norm_dob` accepts, so it is the only spelling a date of birth has once it is
  inside this system — but a date written with a time component is read as an operational
  timestamp and left alone, deliberately, because otherwise every `created_at` in every log line
  would be tokenised without a single personal value being removed.
* **Refs still embed the source's natural key.** `crm:contact:<natural_key>` is emitted verbatim
  under `record_ref`, `source_ref`, `entity_refs` and their siblings, because the evidence model
  is unreadable without them. `natural_key` itself is tokenised, and the sibling pass removes it
  from a ref in the *same* event — but an event that carries a ref and not the key it was built
  from will show whatever the source put in its primary key. Contract SS3/§1.3 pins the generated
  dataset's primary keys as surrogate (`student.id` is a `uuid5` of a sequence index, never
  derived from identity fields), so this is a property of the input, and it is why a source that
  keys on a person would need its ref tokenised too.
* **Surrogate keys are emitted verbatim** (`student.id`, `external_id`, `external_ref`,
  `canonical_id`, `crm_id`, `payment_id`). Contract §1.3 pins `student.id` as a `uuid5` of a
  generator sequence index, never derived from identity fields, so they describe no person — and
  a log that can name no record cannot be debugged.
* **Two `audit_log` writers are outside the chokepoint** (`recon/budget.py`,
  `recon/api/internal.py`) and bind `actor`, `action` and `subject` unredacted. See §4.0.
* **Four `print` sites are outside the console chokepoint** (`recon/budget.py`,
  `recon/bench/__main__.py`, `recon/seed/run.py`, `recon/seed/__main__.py`). None of them writes a
  source record today; nothing enforces that beyond the declaration in
  `recon.logging.UNROUTED_TERMINAL_WRITERS`.
* **Nullity is preserved.** Whether an optional field was present is treated as schema, not as
  personal data, so `"guardian2_email": null` stays null.

```bash
uv run pytest tests/privacy -q          # add DATABASE_URL + KEYSTONE_REQUIRE_DB=1 for the purge tests
```

`tests/privacy/test_leak_hunt.py` is the one that matters most: it generates a real
`--profile dev` dataset, emits every record through the logger every way the service emits one —
nested evidence packet, action payload, interpolated error message, an **exception carrying the
record**, a **formatted traceback**, a rejection's `log_fields()`, a `repr`, and an
`audit_log.detail` — and greps the output for every raw value, its normalised form and every
email local part. One leaked value fails it. It carries a **negative control** — the same sweep
against `LOG_MODE=full` must *find* those values — so a green cannot come from a search that does
not work, and a second control asserts the safe log is not simply empty.

`tests/privacy/test_logging_installed.py` is the one that would have caught the worst defect this
policy has had: `configure_logging()` was called by two test modules and by **no entry point**,
so every test installed the chain itself and passed while the running service ran structlog's
default chain and redacted nothing.

## 6. What is not built

Stated plainly, because a policy that implies more than exists is worse than one that admits a
gap:

* **No subject-erasure ("right to be forgotten") operation.** This policy is time-based only.
  Erasing one named person on request would mean deleting their `entities` row, their
  `entity_links`, their `field_lineage` and their `raw_records` — the mechanics exist (the owner
  principal holds DELETE on all four) but no such function, endpoint or audited workflow is
  implemented, and `entities` deliberately has no time-based window.
* **No scheduled trigger.** `run_purge` is a job with a transaction-owning caller. Nothing calls
  it on a schedule yet.
* **No backup or WAL retention policy.** Purging a row from the live database does not purge it
  from a base backup or from WAL. Keystone runs on Postgres in `infra/docker-compose.yml` with
  no configured backup retention, so there is nothing to state here beyond the fact that a
  production deployment would need this section extended.
* **No encryption-at-rest statement.** Out of scope for this ticket; it is a deployment
  property, not an application one.
